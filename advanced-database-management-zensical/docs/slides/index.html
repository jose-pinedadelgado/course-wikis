Part 1: Why Data Warehouses?

The Problem with OLTP for Analytics

⏱️ ~10 minutes

Your CEO Walks In...

"Show me revenue by department, by quarter, for the last 3 years — and compare it to last year."

In your normalized 3NF database:

  • 5+ JOINs across normalized tables
  • Aggregations across millions of rows
  • Competes with real-time transactions (customers waiting!)
  • Takes minutes to hours
Wrong tool for the job. OLTP is optimized for writes, not reads.

Two Worlds of Data

"The operational systems are where you put the data in, and the DW/BI system is where you get the data out." — Kimball
OLTP (Phase 1)OLAP (Phase 2)
PurposeRun the businessAnalyze the business
UsersApps, clerksManagers, analysts, execs
OperationsINSERT/UPDATE 1 rowSELECT + GROUP BY millions
SchemaNormalized (3NF)Denormalized (Star)
DataCurrent stateHistorical snapshots
RedundancyEliminated ✅Intentional ✅
💡 The big irony: In Phase 1 you fought to eliminate redundancy. In Phase 2, you'll add it back on purpose.

Quick Check: Why Not Just Add Indexes?

🤔 Think-Pair-Share (30 sec): Why can't we just create more indexes on the OLTP tables and run analytics there?
  • Lock contention — Analytical queries lock rows that transactions need
  • No historical data — OLTP only keeps current state (e.g., what was the price last year?)
  • Wrong structure — 3NF requires too many JOINs for aggregation
  • Index overhead — More indexes = slower writes for OLTP

Part 2: Star Schema Design

Kimball's 4-Step Process

⏱️ ~10 minutes

The 4 Steps

#StepQuestion to AskHospital Example
1Business ProcessWhat activity generates events?Patient appointments
2Declare the GrainWhat is ONE row?"One appointment"
3DimensionsWho/what/where/when?Patient, Doctor, Date, Dept
4Facts (Measures)What numbers to measure?Cost, wait_time, Rx_count
⚠️ Kimball's #1 warning: "The most common design error is skipping Step 2. Without declaring the grain, the rest of the design rests on quicksand."

Star Schema Anatomy


                    ┌──────────────┐
                    │  dim_date    │   ← DIMENSION TABLE
                    └──────┬───────┘     (WHO / WHAT / WHEN / WHERE)
                           │             (wide, descriptive, ~1000s rows)
  ┌──────────────┐  ┌──────┴──────────────┐  ┌──────────────┐
  │ dim_patient  │──┤  fact_appointments  │──┤ dim_department│
  └──────────────┘  │─────────────────────│  └──────────────┘
                    │ patient_key     FK  │
  ┌──────────────┐  │ doctor_key      FK  │   ← FACT TABLE
  │ dim_doctor   │──┤ date_key        FK  │     (events + measures)
  └──────────────┘  │ dept_key        FK  │     (narrow, tall, millions of rows)
                    │─── MEASURES ───────│
                    │ visit_count         │
                    │ total_cost          │
                    │ wait_time_min       │
                    └─────────────────────┘

Called a "star" because dimensions radiate outward from the central fact table.

Fact Table Rules

RuleDetails
One row = one eventEach row is a real-world measurable occurrence
Foreign keys to dimensionsOne FK column per dimension
Numeric measuresSUM-able, AVG-able, COUNT-able numbers
Uniform grainNever mix different grains in the same table
No textDescriptive text belongs in dimensions
💡 Fact tables are narrow and TALL (millions/billions of rows, ~5-10 columns).
Dimension tables are WIDE and short (thousands of rows, ~20-50 columns).

Dimension Table Rules

RuleDetails
Surrogate key (PK)Integer, system-generated — not the business key
Wide and flatDenormalized — flatten hierarchies (dept + category + brand all in one table)
Text-heavyVerbose descriptions, not codes
Relatively smallThousands to low millions of rows

Why Surrogate Keys?

  • Business keys change (employee rehired with new ID)
  • Multiple source systems may have conflicting keys
  • SCD Type 2 needs multiple rows for same entity
Exception: dim_date can use YYYYMMDD integer as PK (it's stable and meaningful).

Part 3: Key Details

Facts, SCDs, Star vs Snowflake

⏱️ ~10 minutes

Three Types of Facts

TypeCan SUM across...Example
Additive ✅ALL dimensionsRevenue, quantity, cost
Semi-additive ⚠️Some (not time)Account balance, inventory level
Non-additive ❌NONEUnit price, ratios, percentages

The Unit Price Trap

QtyUnit PriceRevenue
Sale 11$1.00$1.00
Sale 24$0.50$2.00
Total5???$3.00

❌ Average price: ($1+$0.50)/2 = $0.75    ✅ Weighted: $3.00/5 = $0.60

💡 Kimball: "Ratio of the sums, not sum of the ratios." Store components → compute in query.

The Date Dimension

Every star schema needs one. Pre-populate 10-20 years (~7,300 rows).


CREATE TABLE dim_date (
    date_key       NUMBER PRIMARY KEY,  -- 20260318
    full_date      DATE NOT NULL,
    day_of_week    VARCHAR2(10),        -- 'Wednesday'
    month_name     VARCHAR2(10),        -- 'March'
    quarter        NUMBER,              -- 1
    year           NUMBER,              -- 2026
    is_weekend     CHAR(1),             -- 'N'
    is_holiday     CHAR(1),             -- 'N'
    fiscal_quarter NUMBER               -- company-specific
);
💡 Why not just a DATE column? Because you can't GROUP BY is_holiday or filter by fiscal_quarter without a dimension. The dim_date enables slicing time in business terms.

Slowly Changing Dimensions (SCD)

What happens when Dr. Park transfers from Cardiology → Neurology?

TypeStrategyHistory?Use When
Type 1Overwrite old value❌ LostCorrections, don't care about old value

Type 3Add "previous_value" column⚠️ 1 changeOnly need current + previous

Good news: ETL in this course = PL/SQL procedures. You already know how to do this! 

-- Example: Load a dimension (denormalize with JOINs)
CREATE OR REPLACE PROCEDURE load_dim_doctor AS
BEGIN
    DELETE FROM dim_doctor;
    INSERT INTO dim_doctor (doctor_key, doctor_name, specialty, department)
    SELECT d.doctor_id, d.name, s.spec_name, dept.dept_name
    FROM Doctors d
    JOIN Specialties s ON d.specialty_id = s.spec_id
    JOIN Departments dept ON d.department_id = dept.dept_id;
    COMMIT;
END;

Part 4: Analytical SQL Preview

Full deep dive next week — here's a taste of what your star schema enables

ROLLUP — Automatic Subtotals


SELECT NVL(d.dept_name, '** ALL DEPTS **') AS department,
       NVL(doc.doctor_name, '** All Doctors **') AS doctor,
       SUM(f.total_cost) AS revenue
FROM fact_appointments f
JOIN dim_department d ON f.dept_key = d.dept_key
JOIN dim_doctor doc ON f.doctor_key = doc.doctor_key
GROUP BY ROLLUP(d.dept_name, doc.doctor_name);
        

DEPARTMENT     DOCTOR           REVENUE
Cardiology     Dr. Smith        $72,500
Cardiology     Dr. Jones        $49,000
Cardiology     ** All Doctors **$121,500   ← subtotal
Neurology      Dr. Park         $100,500
Neurology      ** All Doctors **$100,500   ← subtotal
** ALL DEPTS **                 $300,000   ← grand total
Without ROLLUP, you'd need UNION ALL of 3 separate GROUP BY queries!

RANK — Top-N Analysis


-- Top 3 doctors by revenue per department
SELECT * FROM (
    SELECT d.dept_name, doc.doctor_name,
           SUM(f.total_cost) AS revenue,
           RANK() OVER (
               PARTITION BY d.dept_name
               ORDER BY SUM(f.total_cost) DESC
           ) AS rnk
    FROM fact_appointments f
    JOIN dim_department d ON f.dept_key = d.dept_key
    JOIN dim_doctor doc ON f.doctor_key = doc.doctor_key
    GROUP BY d.dept_name, doc.doctor_name
) WHERE rnk <= 3;
💡 RANK() = gaps for ties. DENSE_RANK() = no gaps. ROW_NUMBER() = always unique.

🔑 Key Takeaways

  1. OLTP ≠ OLAP — You put data in one, get data out of the other
  2. Star Schema = Fact + Dimensions — facts are events, dims are context
  3. 4-Step Process: Process → Grain → Dimensions → Facts
  4. Never skip the grain! — One row = one clearly defined event
  5. Denormalization is intentional — redundancy speeds up reads
  6. SCD Type 2 preserves history (new row, new surrogate key)
  7. ETL = PL/SQL — You already have the skills from Phase 1
🎯 This gets you hired. Data engineering roles ($150K-$300K+) list star schemas, ETL, and analytical SQL as core requirements.
